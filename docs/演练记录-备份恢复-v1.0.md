## 2. 执行步骤与实测

| 步骤 | 命令 | 结果 |
|---|---|---|
| 1 备份前快照 | 逐表 `count(*)` + 附件 sha256 | 27 表 146 行，2 个附件，指纹已记录 |
| 2 备份 | `make backup` | **838 ms**，产物 `backups/app-20261125T124933-052483.tar.gz`，**15,241 字节**；归档 4 个条目：数据库快照、manifest、2 个附件；清单迁移版本 `0009` |
| 3 模拟灾难 | 移走 `data/app.db`，删除 1 个附件文件 | 数据库不存在（`DB.exists() == False`），附件剩 1 个 |
| 4 恢复 | 解包 → 拷贝数据库与附件回原位 | **8 ms** |
| 5 校验 | `pragma integrity_check` / `foreign_key_check` / 逐表行数 / 附件 sha256 | `integrity_check=ok`；`foreign_key_check` 无违反；**27 表行数全部一致**；**附件指纹全部一致**（2 个，被删的那个也回来了） |
| 6 业务可用性 | 登录 + 5 个页面 + CSV 导出 | 登录 303；`/members`、`/problems`、`/awards`、`/stats/members`、`/members/2/profile` 均 200；CSV 导出 200、688 字节、带 UTF-8 BOM |
| 7 校验器正向 | `python bin/restore_check.py <归档>` | `PASS: integrity_check=ok, foreign_key_check=ok, files=2`，**882 ms** |
| 8 校验器负向 | 归档截断到 4,000 字节后校验 | **退出码 1**，拒绝恢复（见 §4 问题 3） |

## 3. 与目标对比

| 指标 | 目标（设计说明书 §8） | 实测 | 结论 |
|---|---|---|---|
| RPO（可容忍数据丢失） | ≤ 24 小时 | 取决于备份频率；本次备份耗时 0.84 秒，每日一次完全可行 | 满足 |
| RTO（恢复时间） | ≤ 4 小时 | 解包 + 拷贝 **8 ms**，校验 **0.88 s**，业务抽验数秒 | 远优于目标 |
| 完整性 | 数据库与附件可配对 | 27 表行数一致、附件指纹一致、外键无违反 | 满足 |
| 可用性 | 恢复后可登录可读写 | 登录 + 5 页 + CSV 导出均正常 | 满足 |

注：RTO 之所以是毫秒级，是因为数据量只有 405 KB。按验收矩阵的容量估算（三年约 48 万行、150–300 MB），恢复时间会上升，但仍在分钟级，远低于 4 小时。

## 4. 演练发现的问题（按严重度）

| # | 问题 | 影响 | 状态 |
|---|---|---|---|
| 1 | `bin/backup.py` 把上传目录硬编码为 `Path("data/uploads")`，未读 `Settings.uploads_dir`（`app/config.py` 支持 `UPLOADS_DIR`） | 部署时若把上传目录指到别处（如 `/srv/uploads`），备份会**静默漏掉全部附件**，恢复后照片全丢，而归档大小与校验都正常 | 记入 issue，待修 |
| 2 | 没有"就地恢复"命令，只有 `restore_check`（解到临时目录校验） | 真出事时需人工解包并拷贝，步骤正确但容易漏（例如只拷库不拷附件）；缺少 `make restore` 这类一键入口 | 记入 issue，待修 |
| 3 | 归档损坏时 `restore_check` 抛**原始 traceback**（`EOFError: Compressed file ended before the end-of-stream marker`），退出码 1 | 行为安全（确实拒绝恢复），但对值班人不友好，难以分辨"文件坏了"与"程序出错" | 记入 issue，待修 |
| 4 | 备份产物里没有 `data/exports`（导出文件目录） | 导出文件可由数据库重新生成，属可再生物，本次判定为**不需要备份**；但设计说明书 §8 的清单写了"归档导出包"，口径需统一 | 文档待澄清 |

前三条都不影响本次演练结论（数据确实恢复成功），但第 1 条是**真实隐患**：它不会报错，只会在恢复后才发现附件缺失。

## 5. 复现方式

```bash
# 1) 造数据（任意环境，库与上传目录用 data/ 下的默认路径）
export DATABASE_URL=sqlite:///data/app.db UPLOADS_DIR=data/uploads APP_ENV=drill
make migrate && make seed
python /tmp/drill_data.py        # 通过 HTTP 造业务数据；脚本随记录一并保存

# 2) 备份
make backup                      # 产物在 backups/，含 manifest 与 sha256

# 3) 模拟灾难
mv data/app.db data/app.db.lost
rm -f data/uploads/<某个附件>

# 4) 恢复（当前需手工，见问题 2）
mkdir -p /tmp/restore && tar -xzf backups/app-*.tar.gz -C /tmp/restore
cp /tmp/restore/app-*.db data/app.db
cp -r /tmp/restore/uploads/. data/uploads/

# 5) 校验
python bin/restore_check.py backups/app-*.tar.gz
```

## 6. 结论

- **备份可用**：归档包含数据库快照、附件与 manifest，校验和迁移版本齐全。
- **恢复可行**：就地恢复后完整性、外键、行数、附件指纹、登录与业务页面全部通过。
- **时间远低于目标**：备份 0.84 秒、恢复 8 毫秒、校验 0.88 秒，相对 RTO 4 小时有巨大余量。
- **三个待修项已记录**，其中"上传目录硬编码"是唯一会造成数据静默丢失的隐患，建议在下一次切片刻意修掉。
