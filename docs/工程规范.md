# 工程规范

本文件约定目录结构、命名、提交与文档管理方式。改动结构前先改这份文件。

## 1. 目录

```
docs/            需求、设计、评审等文档（Markdown 为唯一源）
docs/adr/        架构决策记录，一条决策一个文件
diagrams/        PlantUML 图源 .puml 与出图 .png（成对提交）
scripts/         出图、文档转换等脚本
src/             源码（技术栈确定后按语言惯例建子目录）
tests/           测试
```

禁止：在根目录堆放过程文件（临时 md、截图、压缩包）。过程材料放 `docs/_drafts/`，该目录不入版本控制。

## 2. 文档

- **Markdown 是唯一源**：docx / pdf 是派生产物，由 `make docs` 生成到 `docs/_build/`。
- 需要交付的成品（如课程提交用的 PDF）可提交到 `docs/`，但必须在同名 md 更新后重新生成。
- 文首写文档信息表：版本、日期、来源、状态。版本号按 `v主.次` 递增，修订理由记在文末变更表。
- 一节只说一件事；表格优先于长段落；数据、数字必须可追溯到来源（原始清单页码、接口返回、实测输出）。

## 3. 图

- 图源用 PlantUML（`.puml`），与 PNG 成对提交，便于复现与改版。
- 图题在图下方，编号 `图 <章>-<序>`；正文引用编号，不写“见下图”。
- 出图统一走 `make diagrams`，不手工导出。

## 4. 提交信息

格式：`<类型>(<范围>): <一句话说明>`，正文写清做了什么、为什么。

| 类型 | 用途 |
|---|---|
| feat | 新功能 |
| fix | 修缺陷 |
| docs | 文档、图 |
| refactor | 重构，不改行为 |
| test | 测试 |
| chore | 构建、依赖、脚本 |

示例：`docs(spec): 需求基线 v1.0，合并 6 组重复功能`

一次提交只做一类改动；不把格式化与功能混在一起。

## 5. 分支

- `main` 保持可读、可交付状态。
- 单一任务开 `feat/<简短描述>` 或 `fix/<简短描述>`，完成后合并回 `main`（个人项目可用快进合并）。
- 不重写已推送的历史；提交历史本身就是过程证据。

## 6. 需求与变更

- 需求变更先改 `docs/需求基线-vN.md`，升版本号并在变更表写明理由，再动代码。
- 技术选型、关键取舍写入 `docs/adr/NNNN-<标题>.md`，格式见模板。
- 原始材料（课程任务、教师要求、接口文档）归档到 `docs/`，不修改原文。

## 7. 待补充（技术栈确定后）

- 代码风格：按所选语言引入格式化与静态检查（如 ruff / google-java-format）。
- CI：`.github/workflows/` 下加 lint + test，跑在 PR 上。
- 依赖锁定：提交 lock 文件。
