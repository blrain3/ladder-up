## 2. 设计目标与约束

本章将基线 §9 的部署、数据、时间与集成约束落实到系统边界。

| 约束 | 设计落实 |
|---|---|
| 校内单机、单应用实例、Docker | 同一台服务器部署应用和本地关系库。只开放 Web 入口，数据库走内部网络。 |
| 百人级会员，无高并发要求 | 以分页、索引和短事务支撑日常工作。以报名截止、批量下发和归档导出作为峰值验收场景。 |
| 附件持久化及每年一次全量备份 | 照片和附件优先用本机挂载目录，落库保存归属、权限和校验信息。年度备份覆盖业务库及归档所需文件。 |
| Asia/Shanghai 及按日任务 | 每日按上海业务日期计算考勤与预警。时刻保存为可还原的统一时间，学期、学年及业务日使用明确的本地日期口径。 |
| 外部服务有配额及可用性限制 | GitHub、Codeforces、Vjudge 通过适配器接入，按平台限流。训练打卡、任务下发和本地数据查询独立于远端同步。 |

单一会员身份贯穿训练、集训、队伍、赛事与归档。业务验收以能够从统计结果追溯到原始记录、规则版本与关键操作为目标。A–E 共 54 个功能点构成基线实施范围，F 的 5 项智能服务属于后续范围，见基线 §2、§4、§5.3。

## 3. 总体架构

本章定义六层职责、依赖方向及六个业务域在架构中的位置。

### 3.1 分层与依赖

| 层 | 职责 | 依赖方向 |
|---|---|---|
| 接入层 | Web 页面与 HTTP API，处理会话、请求格式、分页参数、错误响应与文件流 | 接入层 → 应用层 |
| 应用层 | 编排用例，执行权限检查、事务、跨域调用与审计写入 | 应用层 → 领域层及各域公开接口，经端口使用数据和外部能力 |
| 领域层 | 持有业务实体、值对象、状态迁移规则和数据访问契约 | 领域规则依赖本域模型和小范围共享类型 |
| 数据层 | 实现持久化契约，负责数据库映射、查询索引、迁移与附件元数据 | 数据层 → 领域或应用端口，同时依赖数据库与文件系统 |
| 集成层 | 适配 OJ、GitHub 及后续身份源，转换外部标识与错误 | 集成层 → 应用端口，同时依赖外部平台 |
| 运行保障层 | 装配运行环境、触发作业、检查健康、采集日志、执行备份 | 调度入口 → 应用任务接口，备份工具 → 持久化资源 |

各域业务写入由拥有数据的模块校验并提交。跨域传递本地标识、必要字段和快照版本。底层实现由运行配置装配。数据库事务覆盖状态迁移及其必要的业务记录，网络调用和文件流传输位于事务外。学期、学年和外部账号绑定等共同语义通过有归属的模块接口查询。

### 3.2 六域与图 1-1 的对应

| 域 | 数据输入与输出 |
|---|---|
| A 会员与协会 | 提供会员、部门、状态和归属的只读查询。训练、参赛数据以源域发布结果汇入档案。A 的档案应用服务编排查询，B 的会员查询依赖 A 的主数据接口，两者独立于对方的档案编排。 |
| B 题库与训练 | 只读引用 A。向 C 提供发布版本的题目包，向 E 提供训练记录和测评汇总。 |

| D 赛事 | 接收 E 提供的队伍报名输入，维护报名、名额、赛站和成绩。按队伍标识提供已发布战绩，供队伍档案展示。 |

## 5. 技术选型

本章用统一尺度比较候选技术栈，给出适合单机交付的建议。

本节为建议，最终由 ADR 0002 定稿。评分采用 1～5 分，分数越高表示越适合本项目，四项等权。团队实际技术熟悉度待调查，该列暂统一给中性分 3。部署成本按容器、升级与备份负担评估，生态按认证、迁移、测试和报表配套评估，扩展按事务写入及模块演进评估。评分是设计判断。

| 方案 | 团队熟悉度 | 部署成本 | 生态 | 后续扩展 | 合计 |
|---|---:|---:|---:|---:|---:|
| Spring Boot + MySQL | 3 | 3 | 5 | 5 | 16 |
| FastAPI + PostgreSQL | 3 | 4 | 5 | 5 | 17 |
| Node.js + SQLite | 3 | 5 | 4 | 3 | 15 |

评分阶段推荐 FastAPI + PostgreSQL。定稿时按“规模不构成压力”的事实下调了数据库权重：300 会员、三年约 48 万行、写入以管理员批量录入为主，没有需要行锁竞争的复杂写入。**ADR 0002 已定稿为 Python 3.11 + FastAPI + SQLite + Jinja2/Bootstrap 5，部署为单机 Docker Compose**，PostgreSQL 保留为升级路径。

定稿否决 PostgreSQL 的理由是常驻进程带来的部署与备份负担，而非能力不足；否决 Spring Boot 的理由是课程周期内 JVM 与数据库两套常驻组件的搭建成本高于收益。若团队已有 Java 工程经验，Spring Boot + MySQL 仍是合理选择，评分表中其“后续扩展”一项明显高于其他方案。

SQLite 落地时按 `docs/数据库设计-v1.0.md` 第 4.0 节的方言映射转换 DDL；唯一约束、事务与外键语义不变。

## 6. 关键设计决策

本章记录影响业务一致性、维护成本和数据恢复的主要取舍。

| 问题 | 方案 | 备选与放弃理由 |
|---|---|---|
| 1. 单体还是微服务 | 采用模块化单体。应用单实例按域分包，以公开应用接口约束内部调用。定时执行复用同一应用及用例代码。 | 微服务增加服务发现、网络故障处理、部署及跨服务事务成本，当前数据量与单机约束下收益有限。 |
| 2. 单库还是分库 | 使用一个关系数据库，表及迁移按域归属管理。通过外键、唯一约束和事务维护会员引用、报名及名额一致性，读接口封装跨域访问。 | 按域分库会增加身份引用、事务协调、恢复和年度导出的复杂度。 |
| 3. 定时任务如何运行 | **宿主机 systemd timer 触发一次性容器**（`docker compose run --rm app bin/job <name>`），`Persistent=true` 补跑错过的时间点；每次运行写 `job_run`，同一作业与业务日唯一，重跑复用同一入口。Web 进程内不启动调度器。 | 进程内调度器会随 Web 重启丢失排期、随多副本重复执行；独立消息代理对这种作业量属于过度设计。详见 ADR 0003 第 4 节。 |
| 4. 外部 OJ 拉取还是推送 | 按平台及账号限流拉取。绑定后发起异步同步，定时补拉。按平台及提交标识去重，标识仅账号内唯一时加入账号键。分页写入与游标推进同事务提交，拉取小范围重叠以兼顾延迟到达。 | 推送取决于上游回调能力及校内入站条件。同步请求与打卡同事务会把远端限流传导给用户。 |
| 5. 文件与照片怎样存储 | 挂载私有本地目录，`attachment` 表登记对象键、归属、类型、大小与哈希，业务表存 `attachment_id`。临时写入后原子改名，再提交元数据，按保留窗口清理孤儿文件。下载经资源权限校验。 | 数据库保存大文件会扩大数据库备份与恢复负担。校内对象存储待确认服务与凭据。外链难以保证可访问性和归档可恢复性。 |
| 6. RBAC 还是简单角色判断 | 采用角色绑定权限点、授权范围绑定资源的 RBAC。操作同时校验角色、资源归属、业务状态和字段可见性。 | 在各控制器直接判断角色容易遗漏资源范围，也难处理成员、队长、命题等职责叠加。 |
| 7. 审计日志如何落库 | 关键业务变更和审计行在同一事务写入追加表，记录操作者、对象、动作、差异摘要、时间和请求标识。失败鉴权另记安全日志。 | 仅写文本日志难以证明业务提交与审计一致。独立审计服务增加双写失败场景和运行依赖。 |
| 8. 学年归档如何锁定 | 按学年记录归档状态及版本。预导出绑定数据版本，复核确认时事务内锁定学年控制记录并校验版本。所有涉及该学年的写入及作业共用此控制记录。锁定后补正经授权生成关联更正记录和新归档版本，保留原导出。 | 仅在前端隐藏按钮会遗漏批处理和接口写入。整库只读会阻塞新学年。覆盖原归档使已交付材料无法复核。 |

OJ 达到限额或收到退避提示时暂停该平台的批次，在限速预算内重试。页面展示最近成功时间及待同步状态。题目导入保留来源链接及映射键，自动同步补充证据时保留人工打卡与补卡历史。接口或授权不可用时保留手工登记路径，见基线 §9、§10。

年度导出期间允许正常办理事务，数据有更新时重新生成待确认包。锁定覆盖该学年的档案快照、考核、奖惩、训练、集训、报名和成绩等历史记录。跨学年引用继续指向可追溯的快照，会员当前联系方式可以更新。备份失败时保留锁定版本，标记待备份并重试，校验通过后记录归档完成。

## 8. 非功能设计

本章给出性能验收口径、可用性、数据恢复、日志与安全措施。

| 项 | 建议与验证方式 |
|---|---|
| 负载和响应 | 并发 20 个活跃会话（估算值）。在拟部署单机、百人级会员及覆盖完整学年的构造数据下，常用分页查询 p95 ≤ 500 毫秒，普通表单写入 p95 ≤ 1 秒（均为目标值，待实测）。分开记录本地请求、外部同步和文件导出耗时。 |
| 查询与批处理 | 对会员标识、学年、任务截止、赛事报名状态及考勤日期建立适用索引。归档导出、外部同步走受限后台批次，提供进度和失败原因。用峰值报名叠加一次日任务检查响应及名额一致性。 |
| 可用性 | 单机故障期间服务中断。应用与数据库配置自动重启和健康检查。适配器超时时返回最近成功同步的本地状态，发现同步滞后与日任务漏跑时记录告警。 |
| 数据备份 | 每日一次 `make backup`：先用 Online Backup API 生成 `app.db` 一致快照（不 `cp` 正在写的库），再按该时刻的 `attachment` 清单打包上传目录；升级前额外备份一次。包内附迁移版本与 SHA-256，另存异机副本。备份期间冻结文件回收，避免“清单有、文件已删”。 |
| 恢复验证 | 恢复点不超过 24 小时、恢复时间不超过 4 小时（目标值，待实测）。`make restore-check` 在隔离目录恢复，**分阶段验**：第 3 周（S5）首验 `integrity_check` + `foreign_key_check` + 登录 + 附件抽样；档案导出在 S6 交付后补一次导出抽样（用恢复后的库重导并比对行数）；交付周（M4）完整回归。首次演练不留到交付周。 |
| 日志与审计 | 运行日志记录请求标识、错误、作业时间与结果。审计表记录入退会、权限变动、成绩更正、资格、赛站及归档操作，按角色授权访问。保留期由校方评审确认，日志与归档副本独立管理。 |
| 凭据与隐私 | 凭据（Codeforces 访问、SMTP 可选）以只读文件挂载注入，进程内不落库；SQLite 无数据库账号，文件权限 600、属主为运行用户。日志、预览、导出屏蔽口令、会话 ID 与未授权个人字段。 |
| 越权及内容防护 | 接入启用 HTTPS，服务端验证会话、来源与请求参数。渲染题解时清理不安全 HTML，上传校验内容类型和大小，文件键由服务端生成。以跨部门、跨队伍、越权审批及绕过归档锁作为验收用例。 |

## 9. 部署架构

本章规定单机 Docker Compose 的组件、卷与作业入口，按 ADR 0002 与 ADR 0003 的定稿描述。

系统只有两个容器：应用与反向代理。数据库不是独立服务，而是挂载在应用容器里的一个文件。

| 组件 | 网络与入口 | 卷 |
|---|---|---|
| proxy | 宿主机发布 443 并转发到应用；80 只做 301 跳转到 443，不转发业务请求 | 证书与站点配置只读挂载 |
| app | 只由 proxy 访问；对外仅出站访问 Codeforces | `./data/db:/srv/app/db`（含 `app.db` 与 WAL 文件）、`./data/uploads:/srv/app/uploads`、`./data/exports:/srv/app/exports`、配置只读挂载 |

**没有独立数据库容器、没有数据库账号、没有 `dump` 工具链。** 备份通过应用内的一次性命令完成（SQLite Online Backup API），不以文件复制代替，避免拷到 WAL 未合并的中间态。

启动顺序：`docker compose run --rm app alembic upgrade head` → `docker compose up -d` → `GET /health` 返回 200 才接入流量。升级前先 `make backup`。

定时任务由宿主机 systemd timer 触发一次性容器（`docker compose run --rm app bin/job <name>`），带 `Persistent=true` 补跑漏掉的触发；每次运行写 `job_run`，同一业务日唯一。

## 10. 演进路线

本章把需求范围与工程交付批次对应，明确每个阶段的验收内容和排除项。

基线 §2、§5.3 把 A–E 定为本期范围，将 F 称为二期。基线 §11 另给出 A+B 先行、C+D 随后、E 与 F 后置的工程顺序。下表采用工程期次，二期先打通 C+D，再接入 E 完成联调，三期交付基线后续范围 F。图 1-1 中 F 标注的二期沿用基线 §2 的需求期次。

| 工程期次 | 交付及验收 | 本阶段不做 |
|---|---|---|
| 一期 | 完成 A+B 共 23 项，交付入会、观察期训练、发布任务、打卡、测评及档案主线，具备权限、审计与备份骨架。FR-B-14 依据最近训练记录给规则建议。FR-B-15 按实际可用的 OJ 接口验收，记录失败及补录能力。 | 集训、赛事及组队完整交付，在线支付、MBTI、模型化推荐。 |

## 11. 假设与遗留风险

基线第 10 节的 10 个待确认项已在基线 v1.1 中定稿为决策，技术栈部分见 ADR 0002。本章只保留“决策已定，但仍有残余风险”的条目。

| 事项 | 已定决策 | 残余风险与应对 |
|---|---|---|
| 会员规模 | 按 300 人设计，分页不做缓存 | 若实际超过 1,000 人，打卡类记录年增会逼近单机写入上限；应对是迁移到 PostgreSQL（ADR 0002 复核条件） |
| 身份认证 | 自建账号，保留 `auth_provider` 与 `/auth/sso` 位置 | 密码重置依赖人工，管理员权限集中；应对是初始密码强制修改 + 审计日志 |
| 附件位置 | 本地 `data/uploads/`，统一走 `/files/{id}` | 主机损坏会丢附件；应对是备份脚本把上传目录与数据库一起打包 |
| 外部接口 | 一期只接 Codeforces 公开 API 与 Vjudge 手工导入 | 外部接口变更或限流收紧会导致同步失效；应对是同步失败降级为手工补录并记日志 |
| 考勤终端 | 网页签到 | 可代签；应对是记录时间戳与 IP，异常由管理员复核，不做技术防作弊 |
| 综测口径 | 手工录分值，导出 CSV | 规则变化时需人工重算历史学期；应对是导出前确认规则版本并存档 |
| 名额规则 | 后台可配 `contest_site.quota` | 名额填错会挡住报名；应对是分配前提供“名额余量”预检接口 |
| 实时榜单 | 只记最终成绩 | 赛中无法展示进度；应对是明确列为二期，不承诺 |
| 历史迁移 | CSV 模板 + 一次性脚本 | 旧表格式不统一导致导入错误；应对是导入前给错误行报告，人工修正后重跑 |
| 交付形态 | 一期交付 A+B 可运行系统 | 课程周期内实现量仍然偏大；应对是项目计划第 8 节的质量门槛，功能点不达标就砍范围不加时 |
