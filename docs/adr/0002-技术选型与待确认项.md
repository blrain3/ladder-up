# ADR 0002：技术选型与需求待确认项的处理

- 状态：已接受
- 日期：2026-11-24
- 决策者：项目负责人
- 相关：`docs/需求基线-v1.2.md` 第 10 节、`docs/设计说明书-v1.0.md` 第 5 节

## 背景

需求基线 v1.0 第 10 节列出 10 个未决问题，其中 4 条直接决定技术栈（规模、认证、附件存储、外部 OJ 接口），其余影响交付范围与实现细节。设计说明书第 5 节给出三组候选方案的评分比较，但明确写“最终由 ADR 0002 定稿”。

本 ADR 记录两组决策：一组是技术栈，一组是 10 个待确认项的处理办法。

## 决策一：技术栈

**采用 Python 3.11 + FastAPI + SQLite + Jinja2/Bootstrap 5，植物 UML 用 PlantUML，部署为单机 Docker Compose。**

### 理由

1. **规模不构成压力**。按 300 会员、三年约 48 万行估算，最大两张表是 `audit_log`（20 万）与 `oj_submission`（12 万），打卡表约 3 万行。SQLite 在这种量级下查询在毫秒级，不需要独立数据库进程。
2. **写并发可控**。系统是“少数管理员批量录入 + 会员零星打卡”，不是高并发写入。SQLite 的库级写锁在这里不构成瓶颈；真正需要的唯一约束、事务、外键它都支持。
3. **部署与备份最简**。整个系统 = 一个容器 + 一个 `.db` 文件 + 一个上传目录。备份用 SQLite Online Backup API 生成一致快照（不能直接 `cp` 正在写入的库），恢复是把快照放回去，不需要 `pg_dump` 之类的工具链。
4. **人选与工具链匹配**。后端语言同时承担 Web API、CSV 数据整理、报表与定时任务，一个语言一套依赖即可；实现交给代码代理执行时，Python 生态的样例与文档密度最高。

### 被否决的方案

| 方案 | 否决理由 |
|---|---|
| Spring Boot + MySQL | 需要 JVM 与数据库两个常驻进程；课程周期内搭建与调优成本高于收益。若团队已有 Java 工程经验，此方案仍是合理选择，见设计说明书第 5 节评分。 |
| Node.js + SQLite | 运行时与前端同栈是优点，但本项目前端是服务端渲染，不构成优势；ORM 与迁移工具在事务表达上不如 Python 侧直接。 |
| FastAPI + PostgreSQL | 设计与事务能力最强，但本项目没有需要行锁竞争的复杂写入；多一个常驻进程，换来的是部署与备份负担。**保留为升级路径**：并发写入或数据量超出预期时，按附录映射迁移。 |

### 后果

- `docs/数据库设计-v1.0.md` 的 DDL 以 MySQL 语法书写，作为**逻辑模型基准**；落地 SQLite 时按该文档新增的方言映射表转换。
- 前端不做 SPA，用 Jinja2 模板 + Bootstrap 5；交互较重的页面（报名、成绩录入）用少量原生 JS 或 Alpine.js。
- 数据库升级路径保留：字段类型与约束在逻辑层已与具体产品解耦，迁移只需改方言层。

## 决策二：10 个待确认项

| # | 决策 | 影响 |
|---|---|---|
| 1 | 会员规模按 300 人设计（观察 150 / 正式 120 / 实验室 30） | 列表必须分页；不做缓存 |
| 2 | 自建账号（学号 + 密码），不对接校内统一认证 | 保留 `auth_provider` 字段与 `/auth/sso` 接口位置 |
| 3 | 附件存本地 `data/uploads/`，库中存相对路径，统一走 `/files/{id}` | 换对象存储只改存储适配器 |
| 4 | 一期只接 Codeforces 公开 API 与 Vjudge 手工导入，不做 GitHub 提交抓取 | 限流 1 请求/2 秒，失败重试 3 次后跳过并记录 |
| 5 | 考勤用网页签到，扫码与定位列为二期可选 | 不引入设备依赖 |
| 6 | 综测加分手工录分值，导出 CSV 给学校系统，不对接 | 规则变化不影响代码 |
| 7 | 赛站名额后台可配（`contest_site.quota` + 系统配置） | 不写死规则 |
| 8 | 不接实时榜单，只记录最终成绩（手工或 CSV 导入） | 避免持续轮询外部 OJ |
| 9 | 不做历史数据迁移工具，提供 CSV 模板与一次性导入脚本 | 旧 Excel 格式各异，通用迁移器成本高于整理一次 |
| 10 | 一期内交付可运行的域 A + B（23 个功能点）；C/D/E 交设计与图 | 决定实现范围与排期 |

详细理由与“若变更会怎样”写在需求基线 v1.1 第 10 节，本表只留结论。

## 复核条件

出现下列任一情况时重新评估本 ADR：

1. 会员规模超过 1,000 人，或打卡类记录年增超过 10 万行；
2. 需要多实例部署或对外开放写入接口；
3. 学校提供统一身份认证接口，且接入成本低于自建账号维护；
4. 需要对接实时榜单，且外部 OJ 提供稳定的推送机制。
