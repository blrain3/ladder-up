## 1. 背景与目标

学校 ICPC 集训队的日常事务目前分散在多处：会员登记在 Excel，训练计划在群里口头安排，题目和题解散落在各个 OJ 账号，赛事报名靠人工统计，成绩归档靠个人笔记。同一个会员在报名表、训练表、成绩表里的身份信息不一致；集训考勤与训练打卡各记一套；赛事结束后的队伍战绩没有沉淀。

本系统要做的是把这条链路上的**会员、训练、集训、赛事、组队**五类主数据收进一个系统，形成可追溯的档案，并用统一的数据支撑赛前选拔（谁能参赛、赛站怎么分配）与赛后归档。

目标不是"把 65 个功能都做出来"，而是**建立一套数据一致、流程可查的管理基线**。原始清单里 6 组重复功能需要合并，2 个未编号子系统需要重新定位。

## 2. 范围划分

原始清单的 11 个子系统按业务耦合度收敛为 **6 个域**：

| 域 | 名称 | 来源子系统 | 原始功能数 | 归并后 |
|---|---|---|---|---|
| A | 会员与协会管理 | 1 协会与会员 | 8 | 8 |
| B | 题库与训练管理 | 2 知识点题库 + 3 训练管理 | 17 | 15 |
| C | 集训管理 | 4 寒假集训 + 7 暑假集训 | 14 | 9 |
| D | 赛事管理 | 5 校赛 + 6 非 XCPC + 9 XCPC | 19 | 15 |
| E | 组队管理 | 8 组队管理 | 7 | 7 |
| F | 智能服务（暂缓） | 10 MBTI + 11 个性化推荐 | 9 条目 | 5 |

**设计追踪范围：A–E 五个域共 54 个功能点；课程一期实现 A+B 共 23 个功能点**（§10.10）。54 条全部进入设计与测试追踪，其中 31 条（C/D/E）本期只交设计与图，不交代码。
**F 域（MBTI 与个性化推荐）列为二期**，理由见 5.3。

## 7. 状态机

**会员**：报名中 → 待审核 → 观察会员 → 正式会员 →（竞赛实验室成员）；正式会员 → 已退会；任一状态 → 已除名（违规）。

**队伍**：筹集中 → 组建完成 → 训练中 → 参赛中 → 已解散；组建完成 / 训练中 → 调整中 → 组建完成。

**赛事**：策划中 → 报名中 → 报名截止 → 进行中 → 已结束 → 已归档。

**集训**：筹备 → 进行中 → 已结束。

## 8. 关键流程

1. **入会**：报名 → 资格审核 → 面试 → 录取 → 观察期训练（域 B 的 FR-B-13）→ 转正考核 → 正式会员。
2. **一次训练闭环**：制定计划 → 划分阶段 → 组题目包并下发 → 打卡 → 进度跟踪 → 周测评估 → 更新能力评估。
3. **集训**：定名单与分组 → 排日程 → 每日任务与考勤 → 多校赛报名与成绩 → 总结归档。
4. **参赛**：组队（域 E）→ 赛事报名（域 D）→ 网络预选赛 → 资格确定 → 赛站分配 → 参赛准备 → 比赛跟踪 → 成绩归档。
5. **年度归档**：会员档案 + 成绩 + 奖惩汇总 → 导出交学校 → 数据备份。

## 9. 非功能约束（初步）

- 部署：校内服务器单实例，Docker 容器；无高并发要求（会员规模百人级）。
- 数据：本地数据库；照片与附件存本地或对象存储；每年一次全量备份。
- 时间：所有时间以 Asia/Shanghai 计；考勤、预警按日触发，需一个轻量定时任务。
- 外部依赖：Codeforces 公开接口与 Vjudge CSV 导出（受其限流约束，同步失败不得阻塞主流程）。

## 10. 决策与假设

本章把 v1.0 的 10 个待确认问题全部定稿。每条写四件事：结论、理由、对设计的影响、若日后变更要改什么。技术栈相关的 4 条另见 ADR 0002。

### 10.1 会员规模：按 300 人设计

- **结论**：观察会员 150、正式会员 120、竞赛实验室成员 30，三年内不超过 1,000 人。
- **理由**：集训队的实际规模由学校和赛区决定，不是增长型业务；按 300 人设计留三倍余量。
- **影响**：所有列表接口必须分页（`page` / `size`，上限 100）；不做缓存层。
- **若变更**：超过 1,000 人或打卡记录年增 10 万行，重新评估数据库（见 ADR 0002 复核条件）。

### 10.2 身份认证：自建账号，不对接校内统一认证

- **结论**：学号 + 密码，密码用 bcrypt 存储；会话用**服务端会话表 + HttpOnly Cookie**，有效期 8 小时，不用 JWT。
- **理由**：课程环境无法取得校内 SSO 的接入权限与测试账号；单体 SSR 应用里 JWT 反而多一层——要撤销就得再建黑名单，与直接存会话无异，还多出刷新与浏览器端存储的坑。
- **影响**：新增 `member_session` 表（存会话摘要、过期时间、撤销原因）；写操作校验 CSRF token；`member` 表保留 `auth_provider` 字段（默认 `local`），接口保留 `/auth/sso` 位置不实现；退会、除名、改密即时撤销会话。
- **若变更**：接入 SSO 时新增 provider 适配器，会话机制不变。

### 10.3 附件存储：本地磁盘 + 统一出口

- **结论**：文件存 `data/uploads/<年>/<月>/<uuid>.<ext>`；新建 `attachment` 表登记对象键、归属、类型、大小与哈希，业务表只存 `attachment_id`，对外一律经 `/files/{id}` 读取并校验权限。
- **理由**：单机部署，本地磁盘最省事；统一出口保证权限校验只有一处，不靠“猜 URL”。
- **影响**：上传需限类型（jpg/png/pdf）与大小（单文件 5 MB）；备份脚本要把上传目录一起打包。
- **若变更**：换对象存储只替换 `storage` 适配器，`photo_path` 语义不变。

### 10.4 外部 OJ：一期只接 Codeforces 公开 API 与 Vjudge 手工导入

- **结论**：Codeforces 用公开 API 拉题目与提交；Vjudge 无公开 API，改为管理员导出 CSV 后导入。不做 GitHub 提交抓取。
- **理由**：GitHub 抓取需要 token 与仓库授权，而课程项目里没有真实仓库可抓，做了也无法验证。
- **影响**：同步按 `(platform, external_id)` 幂等；限流 1 请求/2 秒，失败重试 3 次后跳过并记入日志；同步接口异步返回 `taskId`。
- **若变更**：新增平台需实现同一 `OjClient` 接口，并补一条限流配置。

### 10.5 考勤：网页签到

- **结论**：会员登录后点“签到/签退”，记录时间戳；请假走申请与审批。
- **理由**：浏览器定位精度不可靠、可伪造；扫码需要打印与设备配合，都会把“记录考勤”变成“调试设备”。
- **影响**：`camp_attendance` 以 `(camp_id, member_id, att_date)` 唯一；迟到判定由配置的时间窗决定。
- **若变更**：加扫码签到只需新增一次性 token 与一个二维码页面，不改表结构。

### 10.6 综测加分：手工录分值，导出 CSV

- **结论**：奖惩记录带 `extra_points` 字段（可为负），按学期汇总后导出 CSV 交给学校系统。
- **理由**：综测口径每年由学校调整，写进代码等于每年改一次代码。
- **影响**：不实现“自动计算综测总分”，只做“按规则汇总 + 导出”；规则文本存 `sys_config` 便于说明。
- **若变更**：要做对接，需学校提供接口与字段规范，届时新增导出适配器。

### 10.7 赛站名额：后台可配

- **结论**：`contest_site.quota` 由管理员在后台填写，系统只做“不超名额”的校验，不推断名额规则。
- **理由**：名额每年由教练与主办方通知，规则不稳定且无法从历史数据推断。
- **影响**：分配接口在名额不足时返回 40902 并附冲突明细，整体回滚。
- **若变更**：若要按“上一年成绩加权分配”，需先定义权重，属于二期范围。

### 10.8 实时榜单：只记最终成绩

- **结论**：一期录入手工或 CSV 导入的最终成绩与奖项，不接实时榜单。
- **理由**：实时榜单需要持续轮询外部 OJ，失败即告警，运维成本高于收益；课程验收也不看实时性。
- **影响**：`contest_result` 只存最终名次、过题数、罚时、奖项。
- **若变更**：接榜单时新增同步任务与“榜单快照”表，成绩仍以最终录入为准。

### 10.9 历史数据：不做迁移工具

- **结论**：提供两份 CSV 模板（会员、成绩）与一次性导入脚本，导入前人工整理。
- **理由**：旧表由不同人维护，列名与格式各不相同；写通用迁移器的成本高于整理一遍，且只需做一次。
- **影响**：导入脚本做字段校验与错误行报告，不做字段映射配置界面。
- **若变更**：若历史表超过 5 份且格式稳定，再考虑配置化映射。

### 10.10 交付形态：文档 + 可运行的一期系统

- **结论**：一期交付域 A + 域 B（23 个功能点）的可运行系统，含建库脚本、种子数据、启动说明与验收记录；C/D/E 交设计与图，F 只交需求。
- **理由**：验收要求包含“实现的功能”“实现过程”“代码与版本管理”，纯文档无法覆盖；而全部六个域在周期内做完会牺牲质量。
- **影响**：排期按 `docs/项目计划-v1.0.md` 的里程碑执行；一期完成的判定标准写在项目计划第 8 节。
- **若变更**：若只交文档，需同步删减项目计划与测试计划中的实现类条目，避免文档自相矛盾。
